JVM哪些事儿：OOM解毒大全

前言

本文通过模拟OOM实例，通过使用各种相关工具解决OOM问题。

环境

  • JDK 17.0.18
  • Arthas 4.1.8
  • MAT 1.16.1.20250109

什么是OOM?

导致 OOM（OutOfMemoryError）的原因通常对应 JVM 不同的内存区域。简单来说，只要**“内存不够用”或者“内存无法释放”**，就可能触发 OOM。

结合 JDK 版本和内存区域的不同，常见的 OOM 主要分为以下 7 种类型:

错误类型 (Error Message) 对应区域 常见原因
Java heap space 堆内存 对象太多、内存泄漏、堆设置太小
Metaspace (或 PermGen space) 元空间/永久代 加载类过多（如反射、动态代理）
Unable to create new native thread 本地线程 线程数超限、系统资源不足
Direct buffer memory 直接内存 NIO 使用不当、堆外内存泄漏
GC Overhead limit exceeded 堆内存 GC 效率极低，大部分时间在回收但收效甚微
Requested array size exceeds VM limit 堆内存 申请超大数组（超过 int 最大值或 VM 限制）
StackOverflowError (虽不是 OOM 但相关) 虚拟机栈 死递归、方法调用层级过深

解决过程

当监控发现堆内存持续增长且无法释放时，通常可按以下两种场景分析：程序未崩溃和程序已崩溃（发生 OOM）。针对这两种场景，我们介绍对应的分析工具：

  • Arthas：一款强大的 Java 诊断工具，支持在线分析运行中的 Java 程序，无需重启即可实时排查问题。
  • MAT（Eclipse Memory Analyzer Tool）：专业的堆转储分析工具，能快速定位内存泄漏、大对象等内存问题，生成直观的报告。

通过以上工具的组合使用，可以高效定位内存问题的根源，无论是程序运行中还是崩溃后，都能找到对应的解决方案。

¶程序运行中内存过高

下载并运行Arthas

Arthas运行运行后，出现以下信息，选1即可：

输入dashboard，按回车/enter，会展示当前进程的信息，按ctrl+c可以中断执行。

可以重点关注下Memory中的信息：

  • 表头含义

    • Memory：内存区域名称。
    • used：已使用的内存大小。
    • total：当前已申请的内存大小（committed）。
    • max：该区域最大可扩展到的内存大小（-1 表示不限制或由 JVM 自动管理）。
    • usage：使用率（used / total）。
    • GC：与垃圾回收相关的统计信息。

  • 堆内存 (Heap) 区域

    • heap (堆总计)
      • 含义：整个 Java 堆内存的汇总数据。
      • 数据解读：总共申请了 200M，用了 130M，使用率 65.46%。
    • g1_eden_space (伊甸园区)
      • 含义：G1 收集器中新对象诞生的区域。
      • 数据解读：用了 16M，使用率 72.73%。当这里满了会触发 Young GC。
    • g1_old_gen (老年代)
      • 含义：存放存活时间较长的对象。
      • 数据解读：用了 106M，占堆内存的大部分。
      • 关键点：右侧 GC 数据显示 gc.g1_old_generation.count 为 0，说明目前为止从未发生过老年代 GC (Full GC/Mixed GC)，系统还算健康。
    • g1_survivor_space (幸存者区)
      • 含义：存放从伊甸园 GC 后存活下来的对象。
      • 数据解读：使用率 100% (8M/8M)。
      • 注意：虽然显示 100%，但在 G1 收集器中这是正常的。Survivor 区的大小是动态调整的，填满后对象会晋升到老年代，或者触发 GC。只要没报错，暂时不用担心。

  • 非堆内存 (Non-Heap) 区域

    • nonheap (非堆总计)
      • 含义：非堆内存的汇总。
      • 数据解读：使用率 91.49%，较高，主要由 Metaspace 贡献。
    • metaspace (元空间)
      • 含义：存放类的结构信息（类名、方法、字段等）。
      • 数据解读：使用率 99.01% (26M/26M)。
      • 警报：非常高。total 和 used 都是 26M，说明元空间可能达到了初始配额，或者加载的类非常多。如果继续加载类，会触发元空间的 GC，甚至导致 OutOfMemoryError: Metaspace。
    • codeheap_‘non-nmethods’ (代码缓存区)
      • 含义：JVM 用于存储编译后的本地代码（JIT 编译）的区域之一。
      • 数据解读：使用率 22.70%，正常。

  • GC 统计信息 (右侧栏)

    • gc.g1_young_generation.count: 6
      • 含义：年轻代 GC 发生的次数。
      • 解读：发生了 6 次 Young GC，说明系统运行了一段时间，有对象分配和回收。
    • gc.g1_young_generation.time(ms): 169
      • 含义：年轻代 GC 消耗的总时间。
      • 解读：总共停了 169 毫秒，平均每次约 28ms，属于正常范围。
    • gc.g1_old_generation.count: 0
      • 含义：老年代 GC 发生的次数。
      • 解读：0 次。这是好消息，说明老年代还没有满，没有发生耗时的 Full GC。

¶堆转储文件分析（MAT）

拿到 heapdump-live.hprof 文件下载到本地后，使用 Eclipse MAT 打开，按以下步骤操作：

  • 第一步：看自动报告
    • 打开文件后，MAT 会自动生成 Leak Suspects Report。
    • 重点关注：饼图中占比最大的部分，以及下方的 “Shortest Paths To the Accumulation Point”。这是 MAT 自动推断的最可能的泄漏点。
  • 第二步：Dominator Tree
    • 点击工具栏的 Dominator Tree。
    • 操作：按 Retained Heap（保留堆大小）降序排列。
    • 分析：找到占用内存最大的对象。右键点击该对象 -> Path to GC Roots -> exclude all phantom/weak/soft etc. references（排除虚/弱/软引用）。
    • 目的：查看是谁在强引用这个对象，导致它无法被回收。
  • 第三步：Histogram
    • 点击工具栏的 Histogram。
    • 操作：在正则框输入类名（如 com.yourpackage.*）进行搜索。
    • 分析：查看 Objects（实例数量）列。如果某个业务类实例数量异常多（例如几万个小对象），说明存在对象堆积。
    • 后续：右键该类 -> List objects -> with incoming references，查看具体是哪些数据。
