¶客户端配置

启动客户端程序，会发现控制台出现以下错误：

为什么？

在Spring Cloud 2020.0.0版本（Spring Boot 2.4+)引入了新配置加载机制导致的，即不再自动创建bootstrap上下文，需要通过spring.config.import属性显式导入外部配置源。

为什么要这么改动呢？

在2.4版本之前，Spring Boot自身的配置加载机制和Spring Cloud的Bootstrap上下文是两套独立、复杂且嵌套的系统。变更的核心目的是用一套更简洁、一致、强大的机制取代旧的两套模型。

2.4版本之前的问题：

  • 生命周期复杂

    <2.4 版本之前，配置优先级 (bootstrap.yml > application.yml)，即 先启动一个bootstrap上下文加载bootstrap.yml和远程配置（nacos)，然后再启动应用上下文，作为bootstrap上下文的子上下文。这种父子上下文层级结构导致日志、Bean生命周期、属性源查找变得非常晦涩、调试困难。

  • 配置优先级规则晦涩难懂

    配置来源分散，bootstrap 和 application 两个文件中，且与spring.config.additional-location、spring.config.location等属性交互时，优先级规则极其复杂，容易出错。

  • 与Spring Boot原生机制割裂

    Bootstrap 上下文是Spring Cloud引入的一个补丁式解决方案，绕过了Spring Boot原生的ConfigFileApplicationListener等机制。

    使得在增强核心配置系统时，必须额外考虑如何与Spring Cloud的这套“外部系统”兼容，极大程度限制了配置系统的发展。

而2.4版本之后，引入了全新的ConfigDataAPI和统一的spring.config.import协议，旨在从根本上解决上述问题。

  • 单一、线性的配置加载生命周期
    • 一个应用上下文，配置加载过程是从上到下清晰的“管道”。
    • spring.config.import属性允许在加载过程的任何阶段显式地导入其他配置源（如本地文件、Nacos、Consul还是Git)。
    • 配置加载顺序取决于spring.config.import语句的声明顺序，
  • 配置导入是显式声明的
    • 旧版本是隐式的：只要在Classpath加入了spring-cloud-starter-bootstrap，Bootstrap上下文就会自动创建。
    • 新版本是显式的：必须通过spring.config.import=XXX:XXX来明确告诉Spring Boot从哪里导入配置。
  • 与Spring Boot生态深度统一
    • 新的ConfigDataAPI是Spring Boot原生的一部分。Nacos、Consul等配置中心只需要实现ConfigDataLocationResolver和ConfigDataLoader，即可以插件形式无缝插入。
    • 将Spring Boot和Spring Cloud的配置加载扁平化，无论远程还是本地的配置源都处于同一平面，遵循同一套规则进行处理。

¶全新import标准语法格式

  • optinal: 可选，标识该配置文件可选
    • 有optional：如果文件不存在、网络连接不上或解析失败，Spring Boot 忽略错误，继续启动，不会报错。
    • 无optional：默认，如果找不到文、连接失败或解析失败，Spring Boot直接抛出异常并终止启动。
  • protocol：必需，指定配置来源的协议
    • nacos：来自 Alibaba Nacos Config (需引入spring-cloud-starter-alibaba-nacos-config)。nacos启动器里包含，无需重复引入。
    • configserver：来自 Spring Cloud Config Server。
    • file：来自本地文件系统路径。
    • classpath：来自类路径下的文件。
    • http/https：来自远程 HTTP URL 。
  • localtion: 必须，具体的资源标识，格式取决于协议
    • nacos：配置文件的DataID（如 application-dev.yaml，user-service.yaml)
    • file：相对路径或绝对路径 （如 ./config/application.yaml，/etc/myapp/config.yaml)
    • classpath：类路径资源名 （如 config/settings.yaml)
  • params：可选，查询参数，常用于 Nacos
    • 对于 Nacos 协议，可以在后面加? 传递参数，常见参数包括：
      • group：指定 Nacos Group （默认 DEFAULT_GROUP)
      • refreshEnabled：是否开启动态刷新 （true/false，默认 true)

¶监听器+自动刷新

有时间我不想自动刷新某些配置，有些配置又要刷新，怎么处理呢？

换个说法，会更好，我想给某些配置添加监听器，某些又不要。

自动刷新的前提是要存在监听器

监听器的添加，有以下方式：

  • spring.config.nacos.refresh-enable ：全局开关，默认true
  • spring.config.import=nacos:xxx&refreshEnabled=true：针对某个配置是否监听，默认true
  • @NacosConfigListener：注解创建监听器

如果``spring.config.nacos.refresh-enable=false，那么就不会创建spring.config.import=nacos:xxx&refreshEnable=true的监听器，但手动创建@NacosConfigListener`的监听器正常运行，但但是就算代码中加入自动更新的操作，也不会生效。

代码创建的监听器优先级最高。

反之，如果spring.config.nacos.refresh-enable=true，spring.config.import=nacos:xxx&refreshEnable=false并不会创建监听器。

监听器 + 全局开关为true => 自动刷新 。

全局开关不单是监听器创建的开关，还是自动刷新的总开关。

大白话，好比房子里的开关，全局开关就是电闸，每个配置上的refrehEnabled是房间的开关，电闸关了，房间的开关开了也亮不了灯；而自动刷新好比你晚上在房间里看书，如果不把灯打开，你也看不了书；而自动刷新那些注释好比书，有了书才能看书。

如果关闭了监听器，在代码中，用@RefreshScope + @Value、@NacosConfig、@NacosValue、@NacosConfigurationProperties等注解一样无法自动刷新。

所以，要自动刷新和加载一次的配置通过使用spring.config.import的参数refreshEnable=true/false来控制。

常用到的注解：

  • @RefreshScope：类注解， 指明该Bean需要自动刷新
  • @Value: Spring提供的注解，注入配置值，但会受到其他属性源的影响，优先级JVM>ENV>Nacos
  • @NacosValue: 注入配置值，只接收naocs属性源，支持自动刷新
  • @NacosConfig: 类注解，属性注解， 注入配置值
    • 默认支持动态刷新
    • 需要设置目标的dataId和group以及配置种的指定key
    • 不受其他属性源影响，准确度高
    • 支持复杂对象注入，如自定义JavaBean及其集合类型
    • 可用于Bean，类似@ConfigurationProperties
  • @ConfigurationProperties：类注解，可以指定配置前缀
  • @NacosConfigurationProperties:
  • @NacosConfigListener：接收配置变更回调事件
    • 默认不会回调初始值，如需，通过指定initNotify=true

项目使用 Nacos 作为配置中心和服务发现，现在给出一套配置文件模板。

设计配置文件：优先级从低到高

  • 应用本地配置文件：application.yaml
  • 全局配置：nacos:application.yaml，nacos:application-dev/prod/test.yaml
  • 共享中间件配置：nacos:redis-config.yaml，nacos:mysql-config.yaml，nacos:rabbitmq-config.yaml
  • 业务共享配置：nacos:business-common.yaml
  • 应用通用配置：nacos:${spring.application.name}.yaml
  • 应用环境配置：nacos:${spring.application.name}-${spring.profiles.active}.yaml
  • 本地覆盖：file:./application-${spring.profiles.active}.yaml

nacos分组

  • 全局配置：DEFAULT_GROUP
  • 共享中间件配置：MIDDLEWARE_GROUP
  • 业务共享配置：BUSINESS_GROUP
  • 应用通用配置：${spring.application.name}-GROUP
  • 应用环境配置：${spring.application.name}-GROUP

¶应用本地配置文件

resources/application.yaml: 应用运行的基本骨架。

  • 端口
  • 应用名
  • 启用的profile
  • nacos 的 注册中心 和 配置中心 连接配置
  • spring.config.import导入相关配置

针对服务不同，可以适当去除某些配置文件，如网关不需要中间件 mysql 。

这里不由疑问，为什么需要在这里就加入注册中心的配置？放在nacos注册中心，自由操控，岂不妙哉。

其实，Spring Boot启动时，先启动了配置中心检测程序，接着启动注册中心检测程序。

这么说吧，只要加入注册中心的依赖spring-cloud-starter-alibaba-nacos-discovery，就会用默认配置去连接nacos。

如果加入依赖了，但没配置naocs地址，就会出现user not foud类似错误。

所以只能先配置注册中心。

¶全局配置 application.yaml & application-{env}.yaml

定位：团队的标准规范，所有微服务都继承的配置。

  • application.yaml: 所有环境通用
    • 统一的基础设施超时时间：如 Feign/Ribbon 的默认读取超时、连接超时等。
    • 统一的日志格式：格式定义、TraceID打印规则。
    • 公共拦截器/过滤器配置等。

  • application-{env}.yaml：环境差异化

    • 压缩、日志信息、缓存、健康检查和监控细节信息等

¶自定义配置

需要用到的场景：

  • 应用启动时加载配置：只加载一次，后续修改无效

    • spring.config.import=nacos:xxx&refreshEnable=false
    • 或关闭全局开关spring.config.nacos.refresh-enabled=false

  • 需要动态刷新的配置：动态刷新，保持一致性

    • spring.config.nacos.refresh-enable=true + spring.config.import=nacos:xxx&refreshEnable=true

常用到的注解：

  • @RefreshScope：类注解， 指明该Bean需要自动刷新
  • @Value: Spring提供的注解，注入配置值，但会受到其他属性源的影响，优先级JVM>ENV>Nacos
  • @NacosValue: 注入配置值，只接收naocs属性源，支持自动刷新
  • @NacosConfig: 类注解，属性注解， 注入配置值
    • 默认支持动态刷新
    • 需要设置目标的dataId和group以及配置种的指定key
    • 不受其他属性源影响，准确度高
    • 支持复杂对象注入，如自定义JavaBean及其集合类型
    • 可用于Bean，类似@ConfigurationProperties
  • @ConfigurationProperties：类注解，可以指定配置前缀
  • @NacosConfigurationProperties:
  • @NacosConfigListener：接收配置变更回调事件
    • 默认不会回调初始值，如需，通过指定initNotify=true
