2. 引入新API

¶2.1. 结构化并发（Structured Concurrency）(5th预览)

结构化并发核心思想：将运行在不同线程中的相关任务组视为一个单一的工作单元。
假设一个场景：处理一个请求需要并发查询用户信息和订单信息。
旧写法：

旧写法的问题：

  • 错误传播： 一个任务失败，另一个任务会继续运行，导致资源泄露。
  • 取消机制： 需要手动编写复杂代码来传播取消信号。
  • 可观测性： 线程转储中无法清晰看到findUser和fetchOrder是handle的子任务。

新写法：

新写法优点：

  • 自动错误传播与取消：如果子任务失败，join()会立刻抛出异常，并且scope在关闭时会自动取消fetchOrder()任务。
  • 生命周期管理：所有子线程的生命周期都被严格限制在try代码块内，不可能发送线程泄露。
  • ​清晰的代码结构​​：代码真实地反映了任务之间的逻辑关系。
  • 增强的可观测性​​：JVM 能够识别这种结构，并在线程转储中呈现父-子关系。

¶2.2. 作用域值 (Scoped Values)

作用域值：一种允许在线程内及其子线程之间安全、高效地共享不可变数据的新机制。

  • 旨在克服传统ThreadLocal的缺陷。
    • 无约束的可变性：ThreadLocal的值可以被任何能访问它的代码随时修改，导致数据流难以追踪。
    • 无限的生命周期：ThreadLocal的值会持续存在，直到显式调用remove或线程结束。使用线程池时，容易忘记清理，而导致数据泄露到无关任务，引发安全风险或内存泄露。
    • 昂贵的继承：让子线程继承父线程的ThreadLocal变量（InheritableThreadLocal），需要为每个子线程复制数据，当虚拟线程数量极大时，内存开销显著。
  • 为了与虚拟线程（Virtual Threads）和结构化并发（Structured Concurrency）更好配合。

核心特性

  • 一次性写入，不可变：Scoped Value在作用域中被绑定一个值后，在该作用域内就无法被修改。
  • 有限的生命周期：值的可用性由代码的作用域明确界定，仅在ScopedValue.where(...).run(...)（或 .call(...)）所指向的代码块及其内部被调用的方法可见。一旦run方法执行完毕，绑定自动失效。
  • 高性能继承：子线程（通过StructuredTaskScope创建的）可以高效地继承父线程中绑定的Scoped Values，而无需复制数据。
  • 封装性：通过将Scoped Value声明为private static final，从而严格控制哪些代码可以访问（绑定或读取）该共享数据。

新写法：

使用场景：

  • 替代ThreadLocal进行单向、不可变数据传递的场景。
  • 框架上下文传递（如web框架中的请求上下文、用户身份信息）。
  • 可重入检测。
  • 嵌套事务。

但需要可变的线程状态或双向通信的场景，仍然可以采用ThreadLocal。

¶2.3. 稳定值（Stable Values）(预览)

核心概念：延迟初始化不可变数据，结合了final字段的不可变特性和非final字段的初始化灵活性。
旧写法的局限性：

  • final字段：必须立即初始化，导致启动性能问题。
  • 非final字段：可以延迟初始化，但缺乏线程安全性，且无法享受JVM的常量折叠优化。
  • 线程安全模式：如双检锁、类持有者模式；代码复杂，容易出错，且性能不佳。

场景：日志打印延迟初始化场景。
旧写法：双检锁模式

新写法：使用StableValue

3. 性能相关

¶3.1. 紧凑的对象头

在64位架构上，将对象标头的大小从96到128位减少到64位，大大减少内存占用。
使用：仅需-XX:+UseCompactObjectHeaders即可启用。
收益：

  • 减少22%的堆内存占用。
  • 降低8%的CPU时间。
  • 垃圾收集次数减少15%。

¶3.2. AOT加速启动

简化Ahead-of-Time(AOT)缓存的创建过程，从而加速应用程序的启动。
使用：引入一个新的命令行选项 ​​-XX:AOTCacheOutput=<file>​​。
使用方式：

  • ​创建缓存（新方式）​​：java -XX:AOTCacheOutput=app.aot -cp app.jar com.example.App
  • ​使用缓存（保持不变）​​：java -XX:AOTCache=app.aot -cp app.jar com.example.App

¶3.3. 加快应用程序的预热时间

java应用程序在启动后，需要一段时间预热才能达到最佳性能。
因为HotSpot JVM需要在此期间运行程序，收集方法如何被调用的数据（剖析信息），然后即时编译器（JIT）才能根据这些信息优化和编译热点方法。

在训练运行（即一次预先的、非生产环境的程序运行）期间，JVM不仅会缓存类加载和链接信息，还会收集并缓存方法的执行剖析数据。
随后在生产运行中，启动JVM时，这些预先收集的剖析信息会立即可用，以极大加速了预热过程。
执行时间提升19%，而缓存容量仅增加了约2.5%。

4. 监控相关

¶4.1. JFR CPU时间分析 (实验)

在 Linux 系统上为 JDK Flight Recorder (JFR) 引入一种​​实验性​​的、​​更精确​​的 CPU 时间分析功能，通过利用 Linux 内核的 CPU 定时器机制来安全地生成 Java 程序的 CPU 使用情况剖析报告。

​​使用场景与价值：​​

  • ​性能优化：​​ 帮助开发者更准确地识别代码中消耗大量 CPU 周期的“热点”方法（尤其是在高负载成为 CPU 瓶颈时），从而进行有效优化。
  • 生产环境剖析：​​ 通过调整采样率控制开销，使其适用于​​持续生产环境剖析​​或偶尔触发的定时剖析。
  • 工具支持：​​ 生成的 .jfr文件可由 JDK Mission Control (JMC) 等工具分析，生成火焰图等可视化报告。

¶4.2. JFR 协作采样

JFR 是 Java 的 profiling 和监控工具，通过记录事件来帮助开发者分析程序性能（如 CPU、内存消耗）。
采样原理​​：JFR 通过定期（例如每 20ms）采样所有线程的调用栈来生成执行时间剖面。
协作式采样（简单比喻）：从原来的“在高速行驶的汽车上强行检查引擎”（危险且可能出错），变为“让汽车自己开到下一个服务站进行检查”（安全且可靠）。

¶4.3. JFR 方法计时和跟踪

旨在为 Java Flight Recorder (JFR) 引入​​精确的、非采样​​的方法级别性能分析能力。它允许开发者在​​不修改源代码​​的情况下，记录特定方法的每次调用执行时间、调用次数以及调用堆栈信息。
两个新JFR事件：

  • jdk.MethodTiming: 记录方法的调用次数、平均/最小/最大执行时间（统计摘要）。
  • jdk.MethodTrace: 记录单次方法调用的开始时间、持续时间和完整的调用堆栈。
